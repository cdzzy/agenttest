# agenttest LLM-as-Judge 评测手册

> 对齐今日 Trending 项目中“自动评测”“可解释反馈”“持续集成门禁”三类最佳实践。

## 为什么需要混合评测

纯规则断言适合检查：

- 工具是否被调用
- 输出结构是否正确
- 是否命中黑名单词

但对下面这些问题，LLM-as-Judge 更有效：

- 回答是否真的解决了用户目标
- 多轮交互是否保持一致
- 解释是否清晰、是否过度自信
- 研究总结是否区分事实与推断

最稳妥的方式不是“全交给 LLM 判”，而是 **规则断言 + LLM Judge + 人工抽检**。

## 推荐评测三层结构

### 第一层：硬性断言

必须 deterministic：

- 状态码
- schema
- 工具调用次数
- 关键字段存在性
- 禁止行为是否触发

### 第二层：语义评分

建议打分维度：

- task_completion
- factuality
- clarity
- safety
- citation_quality

每个维度使用 1-5 分，并要求 judge 给出一句理由。

### 第三层：失败归因

对于低分样本，额外要求输出：

- 失败类型
- 触发证据
- 是否可复现
- 建议修复方向

## 推荐 Rubric

```text
1. 是否完成用户目标
2. 是否调用了正确工具或在不能调用时如实说明
3. 是否夸大了不确定信息
4. 是否保留了必要的引用或证据
5. 是否给出了下一步可执行建议
```

## CI 接入建议

如果仓库已经有 GitHub Actions，建议把评测分成两档：

### PR 快速门禁

- 只跑确定性断言
- 跑少量代表性 judge case
- 目标是快

### Nightly 深度评测

- 跑全量样本
- 输出维度分数分布
- 保存失败样本与 judge 评语
- 对比前一版本回归

## 结果展示建议

不要只输出“通过/失败”，建议额外生成：

- 总体通过率
- 各维度平均分
- 失败 Top 类型
- 典型好样本 / 坏样本
- 可回归修复建议

## 适合新增的测试集类型

- 工具不可用时的降级响应
- 多来源冲突信息处理
- 安全拒答与合规边界
- 多轮上下文遗失
- 长输出压缩总结质量
